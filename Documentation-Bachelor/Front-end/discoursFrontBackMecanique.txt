                    PITCH PRÉSENTATION - MÉCANIQUE FRONTEND ↔ BACKEND
                         CloudDiagnoze - Communication Client-Serveur
════════════════════════════════════════════════════════════════════════════════

📌 CONTEXTE (15 secondes)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"Avant de rentrer dans les détails, voyons comment le frontend et le backend
communiquent entre eux.

CloudDiagnoze utilise une architecture CLIENT-SERVEUR classique.

Le FRONTEND, c'est ce que l'utilisateur voit dans son navigateur.
Le BACKEND, c'est le serveur qui traite les demandes et gère les données.

Les deux communiquent par des requêtes HTTP."


🎯 VUE D'ENSEMBLE (30 secondes)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[Montrer le diagramme complet]

"Ce diagramme montre les 3 couches principales :

À GAUCHE : le navigateur, avec tous les fichiers JavaScript et HTML.
AU MILIEU : les flèches de communication HTTP.
À DROITE : le backend FastAPI et la base de données.

Le flux est simple :
1. L'utilisateur clique sur quelque chose
2. Le frontend envoie une REQUÊTE HTTP au backend
3. Le backend vérifie l'identité, traite la demande
4. Il retourne une RÉPONSE JSON
5. Le frontend affiche les données à l'écran

Voyons chaque partie en détail."


🔵 LE FRONTEND - CÔTÉ NAVIGATEUR (1 minute 30)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[Pointer la zone bleue à gauche]

"Le frontend est composé de 4 couches principales :

📦 localStorage - Le stockage local
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   C'est la mémoire du navigateur.
   
   J'y stocke deux choses :
   - Le TOKEN JWT (le badge d'identité de l'utilisateur)
   - Les infos utilisateur (email, nom)
   
   C'est persistant : même si on ferme le navigateur, on reste connecté.

🔑 auth.js - Le gestionnaire d'identité
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Ce fichier gère TOUT ce qui concerne la connexion :
   
   - login() : envoie email/mot de passe → reçoit le token → le stocke
   - logout() : supprime le token → redirige vers login
   - getToken() : récupère le token pour les requêtes
   
   C'est le GARDIEN de l'identité.

🛡️ auth-guard.js - Le videur
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Ce script protège les pages sensibles.
   
   Quand on ouvre dashboard.html, auth-guard vérifie :
   → Y a-t-il un token ? Si non → redirection vers login
   → Le token est-il valide ? Si non → redirection vers login
   
   C'est comme un videur de boîte de nuit : pas de badge, pas d'entrée.

📡 api.js - Le messager
━━━━━━━━━━━━━━━━━━━━━━━━
   Ce fichier communique avec le backend.
   
   Il contient des fonctions comme :
   - getEC2Instances() → appelle /api/v1/ec2/instances
   - getS3Buckets() → appelle /api/v1/s3/buckets
   - getScansHistory() → appelle /api/v1/scans/history
   
   IMPORTANT : chaque requête inclut AUTOMATIQUEMENT le token JWT.
   Le backend sait ainsi QUI demande les données.

👉 Ces 4 fichiers travaillent ENSEMBLE. C'est une chaîne :
   localStorage stocke → auth.js gère → auth-guard protège → api.js envoie"


🔗 LA COMMUNICATION HTTP (45 secondes)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[Pointer les flèches au milieu]

"Entre le frontend et le backend, il y a des REQUÊTES HTTP.

➡️ La requête (orange) :
━━━━━━━━━━━━━━━━━━━━━━━━
   Le frontend envoie une requête avec :
   - L'URL (par exemple /api/v1/ec2/instances)
   - La méthode (GET pour lire, POST pour créer)
   - Le TOKEN JWT dans le header Authorization

   C'est comme envoyer une lettre avec son badge d'identité.

⬅️ La réponse (verte) :
━━━━━━━━━━━━━━━━━━━━━━━━
   Le backend répond avec du JSON.

   JSON, c'est un format de données structuré.
   Par exemple : {\"instances\": [...], \"total\": 5}

   Le frontend reçoit ça et l'affiche dans l'interface."


🟢 LE BACKEND - CÔTÉ SERVEUR (1 minute 30)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[Pointer la zone verte à droite]

"Le backend est structuré en plusieurs couches :

🔐 Les Endpoints (points d'entrée)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Ce sont les URLs que le frontend peut appeler.

   /api/v1/auth : pour l'authentification (login, signup, me)
   /api/v1/ec2 : pour les instances EC2
   /api/v1/s3 : pour les buckets S3
   /api/v1/scans : pour l'historique des scans

   Chaque endpoint correspond à une FONCTION Python.

🛡️ Le Middleware de Sécurité
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   AVANT de traiter la requête, le backend vérifie :

   1. Le TOKEN JWT est-il valide ?
   2. N'a-t-on pas dépassé le Rate Limiting ?
   3. L'origine de la requête est-elle autorisée (CORS) ?
   4. Les données envoyées sont-elles valides ?

   Si une vérification échoue, la requête est REJETÉE.

🔧 Les Services Métier
━━━━━━━━━━━━━━━━━━━━━━━
   Une fois la sécurité passée, on traite la logique.

   - scan_engine.py : lance les scans AWS
   - aws_scanner.py : récupère les données depuis AWS
   - security.py : gère les mots de passe et tokens

   C'est le CŒUR de l'application.

📋 Les Modèles et l'ORM
━━━━━━━━━━━━━━━━━━━━━━━
   Les modèles définissent la structure des données :
   User, EC2Instance, S3Bucket, ScanRun...

   SQLAlchemy (l'ORM) traduit les objets Python en requêtes SQL.
   Je n'écris jamais de SQL directement."


🟣 LA BASE DE DONNÉES (30 secondes)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[Pointer la zone violette en bas]

"Enfin, les données sont stockées dans MariaDB.

Les tables principales :
- users : les utilisateurs
- scan_runs : l'historique des scans
- ec2_instances : les instances EC2
- s3_buckets : les buckets S3

POINT CLÉ : Chaque donnée a un user_id.
Quand un utilisateur demande ses EC2, on filtre par SON user_id.
Un utilisateur ne voit JAMAIS les données d'un autre."


🔄 EXEMPLE CONCRET : Afficher les EC2 (45 secondes)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"Prenons un exemple concret. L'utilisateur ouvre le dashboard EC2.

1️⃣  La page dashboard-ec2.html se charge
2️⃣  auth-guard.js vérifie le token → OK, c'est valide
3️⃣  dashboard-ec2.js appelle api.getEC2Instances()
4️⃣  api.js envoie : GET /api/v1/ec2/instances + token JWT
5️⃣  Le backend vérifie le token → identifie user_id = 42
6️⃣  SQLAlchemy cherche : SELECT * FROM ec2 WHERE user_id = 42
7️⃣  Le backend retourne : {\"instances\": [...], \"total\": 5}
8️⃣  dashboard-ec2.js reçoit le JSON
9️⃣  Il met à jour le HTML : affiche les cartes, tableaux, graphiques
🔟  L'utilisateur voit ses 5 instances EC2

Tout ça en moins d'une seconde."


🎬 CONCLUSION (20 secondes)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

"En résumé, la communication frontend-backend suit ce schéma :

📱 Frontend : affiche l'interface, stocke le token, envoie des requêtes
🔗 HTTP + JWT : le moyen de transport sécurisé
⚙️ Backend : vérifie, traite, interroge la base
🗄️ BDD : stocke les données de manière isolée par utilisateur

C'est une architecture classique, propre, et sécurisée.
Chaque partie a sa responsabilité bien définie."

❓ QUESTIONS POSSIBLES DU JURY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: "Pourquoi séparer frontend et backend ?"
R: "Pour la séparation des responsabilités. Le frontend gère l'affichage,
    le backend gère la logique et les données. On peut les faire évoluer
    indépendamment. Et on pourrait même créer une app mobile qui utilise
    le même backend."

Q: "C'est quoi JSON ?"
R: "JavaScript Object Notation. C'est un format texte pour échanger des données.
    Simple, léger, lisible par les humains et les machines. C'est le standard
    pour les APIs web modernes."

Q: "Pourquoi stocker le token dans localStorage ?"
R: "C'est simple et persistant. Même si l'utilisateur ferme son navigateur,
    il reste connecté. Alternative : les cookies, mais c'est plus complexe
    à configurer."

Q: "Comment le backend sait quel utilisateur fait la requête ?"
R: "Le token JWT contient l'identifiant de l'utilisateur. Le backend le décode,
    extrait le user_id, et filtre toutes les requêtes à la base de données
    avec ce user_id."

Q: "Que se passe-t-il si le backend ne répond pas ?"
R: "Le frontend affiche un message d'erreur. J'ai des try/catch partout
    pour gérer les erreurs réseau. L'utilisateur voit 'Erreur de connexion'
    au lieu d'un écran blanc."
