1. VUE D'ENSEMBLE DE L'ARCHITECTURE
═══════════════════════════════════════════════════════════════════════════════

CloudDiagnoze est une application SPA (Single Page Application) qui permet de
scanner et analyser des infrastructures cloud (AWS, Azure, GCP).

ARCHITECTURE:
┌─────────────┐       ┌──────────────┐       ┌─────────────┐
│   Browser   │ ←────→│  Front-end   │←─────→│  Backend    │
│   (HTML/JS) │       │   (design/)  │       │  (FastAPI)  │
└─────────────┘       └──────────────┘       └─────────────┘
                             │                       │
                             ↓                       ↓
                      localStorage             PostgreSQL
                      (JWT Token)              + AWS API

PRINCIPE DE FONCTIONNEMENT:
- Le front-end est une collection de pages HTML statiques avec JavaScript modulaire
- Chaque page est autonome mais partage des modules communs (auth, api, config)
- Les données sont stockées dans une base PostgreSQL via l'API backend
- L'authentification se fait via JWT (JSON Web Token)
- Les scans AWS utilisent STS AssumeRole pour la sécurité

3. FLUX D'AUTHENTIFICATION
═══════════════════════════════════════════════════════════════════════════════

ÉTAPE 1: Inscription (signup.html)
────────────────────────────────────
L'utilisateur arrive sur signup.html et remplit le formulaire:
  - Email
  - Mot de passe
  - Nom complet (optionnel)
  - Nom de l'entreprise (optionnel)
  - AWS Role ARN (optionnel)

→ Appel API: POST /api/v1/auth/signup
  ├─ Paramètres: { email, password, full_name, company_name, role_arn }
  └─ Réponse: { message: "Compte créé avec succès" }

→ L'utilisateur est redirigé vers login.html


ÉTAPE 2: Connexion (login.html)
────────────────────────────────────
L'utilisateur saisit ses identifiants:
  - Email
  - Mot de passe

→ Le formulaire appelle authManager.login(email, password)
  └─ Voir design/js/auth.js (ligne 150)

→ Appel API: POST /api/v1/auth/login
  ├─ Paramètres: { email, password }
  └─ Réponse: {
      access_token: "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
      token_type: "bearer",
      user: { id, email, full_name, company_name, role_arn, ... }
    }

→ Le token JWT et les infos utilisateur sont stockés dans localStorage:
  ├─ localStorage.setItem('clouddiagnoze_token', access_token)
  └─ localStorage.setItem('clouddiagnoze_user', JSON.stringify(user))

→ Redirection vers provider-selection.html


ÉTAPE 3: Déconnexion
────────────────────────────────────
L'utilisateur clique sur "Logout" dans le menu utilisateur.

→ authManager.logout() est appelé
  ├─ localStorage.removeItem('clouddiagnoze_token')
  ├─ localStorage.removeItem('clouddiagnoze_user')
  └─ window.location.href = 'login.html'

4. PROTECTION DES PAGES
═══════════════════════════════════════════════════════════════════════════════

PRINCIPE:
Toutes les pages protégées incluent auth-guard.js qui vérifie automatiquement
si l'utilisateur est connecté au chargement de la page.

FICHIER: design/js/auth-guard.js
────────────────────────────────────

Au chargement de CHAQUE page protégée:

1. Vérification que authManager existe
   └─ Si absent → redirection vers login.html

2. Vérification du token dans localStorage
   └─ Si absent → redirection vers login.html

3. Validation du token auprès de l'API
   → Appel: GET /api/v1/auth/me
     ├─ Header: Authorization: Bearer <token>
     └─ Si 401 (Unauthorized) → Token expiré
        ├─ authManager.clearAuth()
        └─ Redirection vers login.html

4. Si tout est OK → La page se charge normalement
   └─ Les infos utilisateur sont rafraîchies depuis l'API

EXEMPLE D'UTILISATION:
────────────────────────────────────
<!-- Dans dashbord.html -->
<script src="js/config.env.js"></script>
<script src="js/auth.js"></script>
<script src="js/auth-guard.js"></script>  ← Protection automatique !

→ Si le token est invalide ou absent, l'utilisateur ne verra JAMAIS le contenu
   de la page, il sera immédiatement redirigé vers login.html.

6. CONFIGURATION API ET COMMUNICATION
═══════════════════════════════════════════════════════════════════════════════

Le front-end communique avec le backend via une API REST. Toute la logique
de communication est centralisée dans design/js/api.js.

FICHIER 1: design/js/config.env.js
────────────────────────────────────
Définit l'URL de base de l'API selon l'environnement:
  - Production: https://clouddiagnoze.com/api/v1
  - Développement: http://localhost:8000/api/v1

window.API_BASE_URL = 'http://localhost:8000/api/v1';
window.AUTH_API_BASE_URL = 'http://localhost:8000/api/v1/auth';


FICHIER 2: design/js/config.js
────────────────────────────────────
Définit tous les endpoints de l'API:

const API_CONFIG = {
    BASE_URL: window.API_BASE_URL,

    ENDPOINTS: {
        LATEST_SCAN_SESSION: '/scans/latest-session',
        SCANS_HISTORY: '/scans/history',
        SCAN_STATUS: '/scans/status',
        EC2_INSTANCES: '/ec2/instances',
        S3_BUCKETS: '/s3/buckets',
        VPC_INSTANCES: '/vpc/instances',
        RDS_INSTANCES: '/rds/instances',
        ...
    }
};


FICHIER 3: design/js/api.js - Classe CloudDiagnozeAPI
────────────────────────────────────────────────────────
Cette classe centralise TOUTES les requêtes API.

MÉTHODES PRINCIPALES:
─────────────────────
1. request(endpoint, options)
   └─ Méthode générique pour faire des requêtes HTTP
   └─ Ajoute automatiquement le token JWT dans le header
   └─ Gère les erreurs 401 (token expiré) automatiquement

2. getLatestScanSession(scanId)
   └─ GET /scans/latest-session
   └─ Récupère la dernière session de scan

3. getScansHistory(params)
   └─ GET /scans/history?limit=100&service_type=ec2
   └─ Récupère l'historique des scans

4. getScanStatus(services)
   └─ GET /scans/status?services=ec2,s3,vpc
   └─ Vérifie l'état d'un scan en cours

5. getEC2Instances(params)
   └─ GET /ec2/instances?limit=100&latest_only=true
   └─ Récupère les instances EC2

6. getS3Buckets(params)
   └─ GET /s3/buckets?limit=100&latest_only=true
   └─ Récupère les buckets S3

7. getVPCInstances(params)
   └─ GET /vpc/instances?limit=100&latest_only=true
   └─ Récupère les VPCs

8. getRDSInstances(params)
   └─ GET /rds/instances?limit=100&latest_only=true
   └─ Récupère les instances RDS

9. getAllResources(params)
   └─ Appelle getEC2, getS3, getVPC, getRDS en parallèle
   └─ Retourne toutes les ressources en une seule fois

10. getDashboardStats(params)
    └─ Calcule les statistiques du dashboard
    └─ (Total ressources, scans ce mois, moyenne CPU, etc.)

EXEMPLE D'UTILISATION:
─────────────────────
// Créer une instance (déjà fait dans api.js)
const api = new CloudDiagnozeAPI();

// Récupérer les instances EC2
const ec2Data = await api.getEC2Instances({
    limit: 100,
    latest_only: true,
    region: 'eu-west-1'
});

// Le token JWT est AUTOMATIQUEMENT ajouté dans le header !
// Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

GESTION DES ERREURS:
─────────────────────
- Si le token est expiré (401) → Déconnexion automatique
- Si erreur réseau → Exception JavaScript
- Si erreur serveur (500) → Exception JavaScript

FICHIER: design/js/config-scan.js
────────────────────────────────────

Classe ConfigScan qui gère toute la logique.

PROPRIÉTÉS:
───────────
- selectedServices: []     → Liste des services sélectionnés
- selectedRegions: []      → Liste des régions sélectionnées
- userRoleArn: ""          → ARN du rôle AWS (depuis settings)
- pollingInterval: null    → Intervalle pour le polling
- scannedServices: []      → Services en cours de scan

MÉTHODES:
────────────────────────────────────

1. init()
   └─ Initialisation de la page
   └─ Chargement de l'historique des scans

2. toggleService(service)
   └─ Active/désactive un service (EC2, S3, VPC, RDS)
   └─ Met à jour la liste selectedServices[]

3. toggleRegion(region, checked)
   └─ Active/désactive une région
   └─ Met à jour la liste selectedRegions[]

4. toggleAllRegions(checked)
   └─ Sélectionne/désélectionne toutes les régions

5. startScan() ← MÉTHODE PRINCIPALE
   └─ Lance le scan

   VALIDATION:
   ───────────
   a) Vérifier qu'au moins 1 service est sélectionné
   b) Vérifier qu'au moins 1 région est sélectionnée
   c) Vérifier que le Role ARN est configuré
      └─ authManager.getCurrentUser()
      └─ Si pas de role_arn → Redirection vers settings.html

   LANCEMENT:
   ──────────
   d) Désactiver le bouton de scan
   e) Afficher les barres de progression pour chaque service
   f) Appeler scanAllServices(selectedServices)

6. scanAllServices(services) ← SCAN MULTI-SERVICES
   └─ Lance UN SEUL scan pour TOUS les services sélectionnés
   └─ Cela garantit que tous les services auront le même timestamp

   REQUÊTE API:
   ────────────
   POST /api/v1/scans
   {
     "provider": "aws",
     "services": ["ec2", "s3", "vpc"],  ← Tous en une fois !
     "auth_mode": {
       "type": "sts",
       "role_arn": "arn:aws:iam::123456789012:role/CloudDiagnozeRole"
     },
     "client_id": "ASM-Enterprise",
     "regions": ["us-east-1", "eu-west-1"]
   }

   RÉPONSE:
   ────────
   {
     "scan_id": "abc123def456",
     "status": "QUEUED",
     "message": "Scan EC2, S3, VPC démarré en arrière-plan"
   }

   → Le backend lance le scan en tâche de fond (BackgroundTask)
   → Le front-end démarre le polling pour vérifier l'état

7. startScanPolling(services) ← VÉRIFICATION ÉTAT
   └─ Voir section suivante (Polling)

10. SYSTÈME DE POLLING ET PROGRESSION
═══════════════════════════════════════════════════════════════════════════════

PRINCIPE:
─────────
Le scan AWS prend du temps (10-30 secondes). Le front-end ne peut pas attendre
la réponse de l'API, il doit donc vérifier régulièrement l'état du scan.

C'est le POLLING: interroger l'API toutes les 500ms pour savoir si le scan
est terminé.

FICHIER: design/js/config-scan.js → Méthode startScanPolling()
─────────────────────────────────────────────────────────────────

FONCTIONNEMENT:
───────────────

1. INITIALISATION (0-10%)
   ─────────────────────────
   Au lancement du scan, chaque service démarre à 10% de progression.
   └─ updateServiceProgress(service, 10, 0)

2. PROGRESSION ARTIFICIELLE (10% → 70%)
   ─────────────────────────────────────
   Pour donner une impression de fluidité, la progression monte artificiellement
   de 10% à 70% sur 4 secondes.

   setInterval(() => {
     if (progress < 70) {
       progress += 3;  // +3% toutes les 200ms
       updateServiceProgress(service, progress, 0);
     }
   }, 200);

3. POLLING API (toutes les 500ms)
   ─────────────────────────────────
   En parallèle, le front-end interroge l'API pour connaître l'état réel.

   GET /api/v1/scans/status?services=ec2,s3,vpc

   RÉPONSE:
   {
     "completed": false,
     "services_status": {
       "ec2": {
         "completed": false,
         "total_resources": 0
       },
       "s3": {
         "completed": true,
         "total_resources": 12
       },
       "vpc": {
         "completed": false,
         "total_resources": 0
       }
     }
   }

4. MISE À JOUR DE LA PROGRESSION RÉELLE
   ──────────────────────────────────────
   Dès qu'un service est marqué comme "completed" par l'API:

   a) Arrêter la progression artificielle pour ce service
   b) Passer de 70% à 100% en douceur (animation 500ms)
      └─ updateServiceProgress(service, 100, total_resources)
   c) Marquer le service comme terminé
      └─ completeServiceProgress(service)

5. FIN DU SCAN
   ─────────────
   Quand TOUS les services sont "completed":

   a) Arrêter le polling
   b) Afficher une notification de succès
   c) Attendre 2 secondes
   d) Rediriger vers le dashboard
      └─ window.location.href = 'dashbord.html'


BARRES DE PROGRESSION:
──────────────────────

Chaque carte de service (EC2, S3, VPC, RDS) possède:
  - Un overlay de progression (remplissage de gauche à droite)
  - Un badge de pourcentage (0% → 100%)

<div class="service-card" data-service="ec2">
  <div class="progress-overlay" data-progress-overlay="ec2"></div>
  <div class="progress-badge" data-progress-badge="ec2">0%</div>
</div>

MÉTHODES D'AFFICHAGE:
─────────────────────
- showServiceProgress(service)
  └─ Affiche la barre à 0%

- updateServiceProgress(service, percentage, resourcesCount)
  └─ Met à jour la progression (0-100%)

- completeServiceProgress(service)
  └─ Marque le service comme terminé (100% + style vert)

- errorServiceProgress(service)
  └─ Marque le service en erreur (style rouge)

RÔLE ARN AWS:
─────────────
C'est le paramètre le plus important !

Sans Role ARN configuré, l'utilisateur ne peut PAS lancer de scan.

Le Role ARN permet à CloudDiagnoze d'assumer un rôle AWS (STS AssumeRole)

  - s3:ListBuckets
  - ec2:DescribeVpcs
  - rds:DescribeDBInstances

13. INTERACTIONS AVEC LE BACKEND
═══════════════════════════════════════════════════════════════════════════════

Le backend est une API FastAPI (Python) qui gère:
  - L'authentification (JWT)
  - Le stockage des données (PostgreSQL)
  - Les scans AWS (boto3 + STS AssumeRole)

FICHIER: CloudiagnozeApp/main.py
────────────────────────────────────

ROUTES PRINCIPALES:
───────────────────

1. AUTHENTIFICATION (api/endpoints/auth.py)
   ─────────────────────────────────────────
   POST /api/v1/auth/signup
   POST /api/v1/auth/login
   GET /api/v1/auth/me
   PATCH /api/v1/auth/me

2. SCANS (api/endpoints/scan.py)
   ────────────────────────────────
   POST /api/v1/scans
   GET /api/v1/scans/status?services=ec2,s3
   GET /api/v1/scans/history?limit=100
   GET /api/v1/scans/latest-session

3. RESSOURCES (api/endpoints/scan.py + events.py)
   ───────────────────────────────────────────────
   GET /api/v1/ec2/instances
   GET /api/v1/ec2/instances/{id}
   GET /api/v1/s3/buckets
   GET /api/v1/s3/buckets/{name}
   GET /api/v1/vpc/instances
   GET /api/v1/rds/instances

ISOLATION DES DONNÉES:
──────────────────────
Toutes les routes (sauf signup/login) nécessitent un token JWT.

Le token JWT contient le user_id de l'utilisateur connecté.

Le backend filtre AUTOMATIQUEMENT toutes les données par user_id:
  → L'utilisateur A ne voit QUE ses propres scans et ressources
  → L'utilisateur B ne voit QUE ses propres scans et ressources

Cela se fait via la dépendance `current_user: User = Depends(get_current_user)`

EXEMPLE:
────────
async def get_ec2_instances(
    current_user: User = Depends(get_current_user)  ← Injection du user
):
    # Filtrer par user_id automatiquement
    instances = db.query(EC2Instance)\
                  .filter(EC2Instance.user_id == current_user.id)\
                  .all()
    return instances


SCAN AWS:
─────────

Quand un scan est lancé (POST /scans):

1. Le backend reçoit la requête avec:
   - provider: "aws"
   - services: ["ec2", "s3"]
   - auth_mode: { type: "sts", role_arn: "..." }
   - regions: ["us-east-1"]

2. Le backend démarre une tâche de fond (BackgroundTask)
   └─ Cette tâche va appeler scan_list_service()

3. scan_list_service() (dans api/services/scan_engine.py):
   a) Assume le rôle AWS avec boto3.STS.assume_role()
   b) Pour chaque service (ec2, s3, ...):
      - Créer un scanner spécifique (EC2Scanner, S3Scanner, ...)
      - Appeler scanner.scan(regions)
      - Sauvegarder les résultats dans PostgreSQL
   c) Marquer le scan comme "completed"

4. Le front-end interroge GET /scans/status pour savoir si c'est terminé

5. Quand terminé, le front-end récupère les données:
   GET /ec2/instances → Retourne les instances scannées
